Coding Agents 101: the art of getting things to ship.

A coding agent isn't magic, but it's the closest thing we have right now. And still, some people get twice the work out of the same tool as the person sitting next to them. This is what those people do differently: how they brief it, what they hand it, how they read what comes back, and when they stop.

About this guide

Tool-agnostic

Everything here works with any current coding agent: Claude Code, Codex, Antigravity, Cursor, opencode, or whatever ships next month.

Tactical

Advice you can try this afternoon, with a concrete example for each. Theory kept to a minimum.

Technical

Written for people who write code and already get around with Git and a terminal.

Tools for writing code with AI have changed four times in ten years. First came autocomplete: method names, imports, mechanical refactors. Then copilots, which wrote the next few lines. Then chats, which generated whole files to copy and paste. Today it's agents: programs that take a description, read your repo, edit, run commands, see the error, fix it, and hand you a change ready for review.1

The thing that changed at each step wasn't how much code the tool writes. It was who runs the loop. With an agent, the reading, doing and checking happens on its side, and you step in when it finishes or when it asks for permission. That turns every engineer into something like the manager of a small team, with tasks running in parallel and a lot more reviewing than typing.

Adapting takes a while. The people who get the hang of it fastest, in my experience, aren't the ones who know the most about AI. They're the ones who know their own code best and are already used to delegating and reviewing: senior engineers, tech leads. This guide collects what they do, so you don't have to find it out the hard way.

Getting started

How to brief it

If you take one section away from this guide, make it this one. A prompt is the briefing you'd give someone who joined the team today and has never seen your code. Write it like that.

Say how, not just what

Think of the agent as a very fast junior whose judgment isn't always reliable. Simple tasks can be described directly. For anything that isn't simple, give it the approach up front: the architecture, the logic, where each piece goes. It raises the odds it comes out right, and it also cuts your review time, because you already know the plan you're reading.

Example

Instead of "add tests", say which functionality to test, which edge cases matter, and what to mock, if anything.

Tell it where to start

Think about where you'd start. Even if you don't remember the exact file name, mention the module, the relevant docs and the pieces involved. Every hint you give is a search it skips, and often an invented approach you avoid.

Example

"Add support for Google's models. Look at the docs at this link and create the implementation in the providers folder, following the pattern of the OpenAI file."

Anticipate where it will get confused

Imagine handing the same prompt to someone who joined last week. Where would they get lost? What would they assume that isn't true? Anything you know that isn't written down, the agent will guess, fast and with total confidence. Write it down first.

Example

"Fix the C++ bindings for the search module so the new tests pass. Heads up: you need to recompile the bindings every time you change the code before testing."

Give it a way to check itself

A large part of the magic of an agent is that it fixes its own mistakes by iterating against an error message. Anything that gives it fast feedback makes it better: types, a linter, tests, a command that starts the project. Teach it to run the team's checks and make sure it has the packages and permissions to do so. If it can open a browser, tell it how to start the frontend.

Example

Moving an untyped Python SDK to typed Python is an improvement the agent benefits from on every task after. That migration is a good task to hand it, by the way.

Give it a place to put what it doesn't know

An agent that doesn't know something writes it anyway, in the same confident tone it uses for what it does know. If you don't give it a place for doubt, it buries the doubt in the normal text, and then you can't tell them apart. Ask it to separate them.

Example

"Only state things you can verify by reading the repo. If you aren't sure, put it under a ## Unconfirmed section instead of making it up." This doesn't cure the habit of inventing; it moves the invention to where you see it today and not in production.

Use what you know

All of the above is easier when you know the code. Even simple tasks come out better if you can verify the logic and the result. And one thing doesn't change no matter how much the tools improve: responsibility for what gets merged is yours. Owning the code and checking it stays human work, probably the most important kind there's.

Getting started

The agent in your day to day

Once you know how to talk to it, it's time to fold it into the routine. These are the uses that pay off fastest.

Start with the boring stuff

Renaming something across forty files, updating docs after a change, writing the tests nobody wrote, finding which commit broke something. These are tasks where the result is verified by running a command and getting it wrong is cheap. This is where an agent gives you back whole hours, and you keep the work that needs a brain.

Example

A common pattern: the engineer ships the change and an agent updates every doc and every piece of interface copy that change touches.

Handle what lands on you out of nowhere

Someone on the team writes "can we do X real quick?" or "Y needs a tweak". Instead of letting it pull you out of what you were doing, send the investigation or the change to an agent and stay on your task. Come back when it finishes. Same for that side-project idea, that prototype, or that script to pull some data: delegate and review later.

Get out of analysis paralysis

Not sure whether a refactor actually simplifies things? Torn between two architectures? Ask it to implement both. Comparing two working implementations is far easier than debating two ideas, and nobody's feelings get hurt when you throw one away.

Example

Undecided between two libraries for a text editor, a team had an agent implement each. The one with the better end result won. It wasn't the one that had sounded better in the meeting.

Have one command that brings everything up

If every pull request produces an environment where you can see the change running, reviewing an agent's work goes from reading a diff to using the product. For frontend changes that's the difference between "looks fine" and "works". If you don't have preview deployments, at least have a single command that starts the project locally, and teach it to the agent.

Delegating more

Larger tasks

Once a task stops fitting in a handful of files, doing it in a single pass stops working. And yet medium and large tasks, one to six hours of work, are where an agent pays off most. You stop saving minutes and start getting afternoons back.

Let it write the first draft

For a substantial task, a first draft by the agent gets the work moving and removes most of the effort. The condition is communicating the approach up front. Think of an architect directing a junior developer. Clear instructions up front save you an afternoon of correcting a misunderstanding at the base.

Heads up

Large tasks aren't hands-off yet. Expect two or three rounds of feedback and a final touch of your own. A realistic goal is saving something like eighty percent of the work. Your judgment still verifies and signs off.

Plan with it before it writes

For complex or vaguely defined tasks, building the plan together with the agent works very well. It's fine if you don't know every requirement at the start. Begin with discovery questions: "how does authentication work here?", "which services would be affected?". Ask it to identify the concrete files it would touch, so you can confirm them before it writes a line.

Almost every agent has a mode that only reads and proposes, without touching anything; it's usually called plan mode. Start there for any task that doesn't fit in one sentence.

Set checkpoints

For work in several parts, especially across layers or repos, define explicit stops:

plan → one chunk → test → fix → you review → next chunk

Ask for a pause after each significant phase. Use it to confirm it's going where you expected, clear up doubts ("explain the auth flow and confirm it's secure") and correct course early, before a mistake at the base spreads to everything else.

Example

"This feature touches the database, the backend and two interfaces. First plan the schema change and tell me when it's ready, so I can apply the migration myself." → "Now the backend, with tests covering X and Y. Tell me when you're done." → "Now both interfaces, calling the new endpoint."

Teach it to verify its own work

When giving feedback, don't stop at "this doesn't work". Explain how you tested it, so next time it can test it itself. And if it's a procedure you'll repeat, write it where the agent always reads it (see Environment and knowledge).

Put tests where the agent touches most

Today an agent doesn't interactively test every scenario. Raising coverage exactly in the areas it modifies most buys you cheap confidence: with solid tests, code that looks correct can be merged without that knot in your stomach. It already writes the happy-path tests; yours are the error cases, the empty inputs, the negatives.

Example

Before handing an agent the translation of a critical piece of Python to C, a team first strengthened the unit tests for that piece. The translation afterwards was boring. Boring was the goal.

Delegating more

Context and sessions

The word that explains most of an agent's behavior is context: what it can see right now. That's not the same as what's in your repo; it's only what it actually read. The gap between those two explains almost every bad answer you'll get.

Ask it what it read

When it gives you a weak answer, the natural reaction is to think the model is dumb. It almost never is. It answered without opening the file that matters. One line at the end of the prompt helps a lot here: "when you're done, list the files you opened to answer". It shows you what went into the context and, more usefully, what stayed out. The list surprised me every time when I started.

A session is everything it has accumulated

Every file it read, everything you said, every error it saw. That's useful at first and a liability later. A long, confused session doesn't get fixed by explaining better. If you've corrected it three times and it's still doing the same thing, stop arguing and open a new session, telling it exactly what to read and what the goal is. Hardly anyone does this, and it works better than anything else I know.

Example

"Let's start over. Only read these files: [list]. The goal is [one sentence]. Don't touch anything else."

What you want it to always know, write down

Since every session starts from zero, anything you want it to know always has to live in a file it reads on startup. Almost every agent has one: AGENTS.md, CLAUDE.md, a rules file.2 The hard part isn't writing it, it's keeping it short. Only what can't be inferred from the code, and only lines that change what it does. If you can delete a line without the agent making a mistake, delete it.

Automating

Workflows that run on their own

An agent reacts to events much faster than a person does, and it's a lot more willing to do boring, repetitive work than anyone on your team.

What you repeat twice, write down

Every team has routine tasks that come back every week: removing a feature flag, bumping dependencies, adding tests to new PRs. Those are the candidates. Someone experienced writes a solid reusable prompt once,3 and from then on it gets run instead of rewritten.

Example

Some teams automatically trigger several agents dedicated to writing tests every time a PR with a new feature is opened.

Review against your own mistakes

There are tools specialized in reviewing PRs fast. But an agent that already knows your repo can give you something more useful: a review against the mistakes your team actually makes.

Example

Keep a list in the repo of the team's most common mistakes, the ones a linter can't catch. An agent reads it and reviews every new PR against it.

React to alerts and incidents

An agent can also trigger on its own when something happens: a new error in production, an alert, a ticket. Almost all of them expose a CLI or an API for wiring them into a workflow, and with MCP they can read logs from external services.

Heads up

For production triage, an agent debugging is weak. Instead of asking it to fix bugs end to end as they arrive, ask it to flag the most suspicious errors and changes. You make the call.

Automating

Environment and knowledge

The same environment as the team

Nothing slows an agent down more than an incomplete environment or one that differs from yours. Align it with the team's: language versions, dependencies, automated checks. Pre-commit hooks installed, secrets and variables loaded automatically, the same linter you run.

Example

A browser with sessions already signed in saves the agent, and you, every manual login while testing.

Your own scripts and MCP

MCP is the standard way to connect external tools: your database, Jira, Sentry, your email.4 It's quick to try and there are servers for almost everything. But many people overlook something simpler: a CLI script. A script that pulls a ticket's info given its ID. A script that restarts the local environment. Small, boring tools for the parts of the workflow that repeat.

Example

A team wrote a script that shows only the first failing test, with that error's full detail. The agent focuses on one at a time instead of drowning in a hundred lines of output, and finishes long tasks faster and more often.

Feed its knowledge base

If the agent makes the same mistake twice, it's time to write the feedback where it always reads it. Don't give it only the framework's rules: tell it the project's architecture, what kind of tests are expected for each kind of task, how the important commands are run and which tools you prefer.

Example

Documenting the exact procedure for adding a new route, with every place boilerplate goes in frontend and backend, turns that task into something you delegate without thinking.

In practice

What it still does badly

Debugging

A bug report looks simple and rarely is. Many bugs need access to logs and databases, and a level of instinct most agents don't have today. If you use it to debug, ask for a list of probable causes instead of having it fix everything itself. You pick the real one; you know the system. Once the cause is known, the fix itself can go back to the agent.

Fine visual work

Today's models don't have the visual reasoning to match a design to a screenshot or a Figma mockup at the level of detail that's needed. They do well when the visual can be described as code: components, a design system, named classes. If you want it to respect your style, give it a design system to work from rather than an image.

Anything released after its training

When working with a new library or a recent version, give it the link to the current docs. Otherwise it assumes the old patterns, because it doesn't know a new version exists. A good agent gets past this if you hand it the docs. None of them go looking on their own.

In practice

Wasting less time

Not every run goes well. There's real variance, and part of the job is learning to steer toward the runs that work and cut short the ones that don't.

Cut your losses early

The most common beginner mistake is insisting a conversation succeed when the agent has already drifted. If you catch yourself thinking "it's ignoring what I said" or "it's going in circles", that's the signal. Sending more messages almost never fixes it. Usually it means the task is bigger than what the agent can handle today. Close it and take over by hand.

Diversify at the start

If you're just starting, spread your bets. Try different tasks and prompts. You find out fast what it's good at with your code and what it isn't. Double down on the first and drop the second. You don't owe the tool a win every time.

Start over more than you would with a person

With a human, restarting the conversation is rude. With an agent it's the most effective tool you have. If you gave it a task and it struggles to correct course, a clean session with all the instructions up front gets further than a long one full of corrections. An agent fixes a tangled environment far worse than it writes code from scratch.

In practice

Security and permissions

Start by asking for everything

Every agent has a permission mode: how much it can do without checking with you, from asking permission for every command to asking for nothing. It's a dial rather than a switch, and where you set it depends on how much you trust the task, more than the tool. For the first month, have it ask for everything. Every permission you approve teaches you what it's about to do, and skipping permissions with a "never ask" flag is the fastest way to learn the expensive lesson.

Branch before touching

Before letting it edit a repo that matters, a new branch. That's the net that turns "it touched files I didn't expect" into a non-event. Discard and move on.

Accounts of its own

A throwaway email is fine for testing sites without risk. If it needs cloud resources, give it a role of its own with the minimum it needs. Never your own credentials.

Nothing in production

The agent works where you test: local, dev, staging. Ideally with the same test setup as the rest of the team. Avoid giving it access to production services entirely. With remote agents, take advantage of the isolated test environment they can run on their own machine.

Read-only keys

Wherever possible, read-only access. And any script that talks to an outside service, you run by hand even if it wrote it. A boring rule. You'll be glad of it the one time it matters.

In practice

What comes next

Engineers aren't going anywhere. As agents keep improving, actually knowing how your system works is worth more, not less. Owning your projects and having judgment about them is what turns an agent from a text generator into a multiplier.

What does change is the shape of the work. Overseeing several tasks in parallel, reviewing more than you write, deciding scope instead of typing implementations. On the teams that are ahead, that's already the job. This guide is what I've learned getting ready for it. Hopefully it saves you a few bruises.

Notes
  1. Examples of autonomous agents today: Claude Code, Codex, Antigravity, Devin, Jules, Cursor in agent mode, opencode. Local ones can be run on several copies of the repo at once for the same parallelism effect as remote ones.
  2. The name changes by tool: AGENTS.md is the most widespread, Claude Code uses CLAUDE.md, Cursor has its rules, Copilot its instructions. What goes inside is the same.
  3. Each tool names it differently: skills, playbooks, slash commands. All of them are a saved prompt with a name, invoked instead of rewritten.
  4. MCP, the Model Context Protocol, is the open standard for connecting external tools to an agent. Every connected server costs the agent context in every session, so connect the ones you use, not the ones that exist.
