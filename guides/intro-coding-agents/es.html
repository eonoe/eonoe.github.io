Coding Agents 101: el arte de que las cosas salgan.

Un coding agent no es magia, pero es lo más parecido que hay ahora mismo. Y aun así hay gente que le saca el doble de trabajo que la persona de al lado, con la misma herramienta. Esto es lo que esa gente hace distinto: cómo le pide, qué le delega, cómo lee lo que le devuelve y cuándo para.

Sobre esta guía

Agnóstica

Lo que dice aquí sirve con cualquier coding agent de hoy: Claude Code, Codex, Antigravity, Cursor, opencode o el que salga el mes que viene.

Táctica

Consejos que puedes probar esta tarde, con un ejemplo concreto para cada uno. La teoría, la mínima.

Técnica

Está escrita para gente que escribe código y ya se mueve con Git y una terminal.

Las herramientas para escribir código con AI han cambiado cuatro veces en diez años. Primero fue el autocomplete: nombres de métodos, imports, refactors mecánicos. Después los copilots, que escribían las próximas líneas. Después los chats, que generaban archivos enteros para copiar y pegar. Hoy son los agents: programas que reciben una descripción, leen tu repo, editan, corren comandos, ven el error, lo corrigen y te entregan un cambio listo para revisar.1

Lo que cambió en cada paso no fue cuánto código escribe la herramienta. Fue quién corre el loop. Con un agent, el loop de leer, hacer y comprobar lo corre él, y tú entras cuando termina o cuando pide permiso. Eso convierte a cada ingeniero en algo parecido a un manager de un equipo pequeño: tareas en paralelo, revisiones, decisiones de alcance.

Adaptarse toma su tiempo. La gente que más rápido le agarra el truco, por lo que he visto, no es la que más sabe de AI. Es la que mejor conoce su propio código y ya está acostumbrada a delegar y a revisar: ingenieros senior, tech leads. Esta guía junta lo que ellos hacen, para que no tengas que descubrirlo a golpes.

Para empezar

Cómo pedirle las cosas

Si de esta guía te llevas una sola sección, que sea esta. Un prompt es el briefing que le darías a alguien que entró al equipo hoy y no ha visto tu código. Escríbelo así.

Dile cómo, no solo qué

Piensa en el agent como un junior muy rápido cuyo criterio no siempre es confiable. Las tareas simples se describen directo. Para las que no son simples, dale el enfoque de entrada: la arquitectura, la lógica, dónde va cada cosa. No solo sube la probabilidad de que salga bien; también te ahorra tiempo de revisión, porque ya conoces el plan que estás leyendo.

Ejemplo

En vez de "agrega tests", di qué funcionalidad probar, qué casos borde importan y qué hay que mockear, si algo.

Dile por dónde empezar

Piensa por dónde empezarías tú. Aunque no recuerdes el nombre exacto del archivo, menciona el módulo, la documentación relevante y las piezas involucradas. Cada pista que das es una búsqueda que se ahorra y un enfoque inventado que evitas.

Ejemplo

"Agrega soporte para los modelos de Google. Mira la documentación en este link y crea la implementación en la carpeta de proveedores, siguiendo el patrón del archivo de OpenAI."

Anticipa dónde se va a confundir

Imagina que le das el mismo prompt a alguien que entró la semana pasada. ¿Dónde se perdería? ¿Qué daría por hecho que no es así? Todo lo que tú sabes y no está escrito, el agent lo va a adivinar, y adivina rápido y con seguridad. Escríbelo antes de que lo adivine.

Ejemplo

"Arregla los bindings de C++ del módulo de búsqueda para que pasen los tests nuevos. Ojo: hay que recompilar los bindings cada vez que cambies el código antes de probar."

Dale una forma de comprobarse

Buena parte de la magia de un agent está en que corrige sus propios errores iterando contra un mensaje de error. Todo lo que le dé feedback rápido lo hace mejor: tipos, linter, tests, un comando que levanta el proyecto. Enséñale a correr las verificaciones del equipo y asegúrate de que tiene los paquetes y los permisos para hacerlo. Si puede abrir un browser, dile cómo levantar el frontend.

Ejemplo

Pasar un SDK de Python sin tipos a Python tipado es una mejora que el agent aprovecha en cada tarea siguiente. Esa migración, de paso, es una buena tarea para dársela a él.

Dale un lugar donde poner lo que no sabe

Un agent que no sabe algo te lo escribe igual, con el mismo tono seguro con el que escribe lo que sí sabe. Si no le das un sitio para la duda, la mete en medio del texto normal y ahí ya no la distingues. Pídele que lo separe.

Ejemplo

"Solo afirma cosas que puedas verificar leyendo el repo. Si no estás seguro, ponlo bajo una sección ## Sin confirmar en vez de inventarlo." No le quita la maña de inventar; mueve el invento a donde lo ves hoy y no en producción.

Usa lo que tú sabes

Todo lo anterior es más fácil cuando conoces el código. Hasta las tareas simples salen mejor si puedes verificar la lógica y el resultado. Y hay algo que no cambia por mucho que mejoren las herramientas: la responsabilidad por lo que se mergea es tuya. Ser dueño del código y verificarlo va a seguir siendo trabajo de humanos, y probablemente el más importante.

Para empezar

El agent en tu día a día

Cuando ya sabes hablarle, toca meterlo en la rutina. Estas son las formas que más rápido se pagan.

Empieza por lo que aburre

Renombrar algo en cuarenta archivos, actualizar la documentación después de un cambio, escribir los tests que nadie escribió, buscar en qué commit se rompió algo. Son tareas donde el resultado se verifica corriendo un comando y equivocarse cuesta poco. Ahí un agent te devuelve horas enteras, y tú te quedas con el trabajo que sí requiere cabeza.

Ejemplo

Un patrón común: el ingeniero manda el cambio y un agent actualiza toda la documentación y los textos de la interfaz que ese cambio afecta.

Atiende lo que llega de golpe

Alguien del equipo escribe "¿podemos hacer X rápido?" o "hay que ajustar Y". En vez de dejar que te saque de lo que estabas haciendo, mándale la investigación o el cambio a un agent y sigue en lo tuyo. Vuelves cuando termine. Lo mismo con esa idea de proyecto, ese prototipo o ese script para bajar unos datos: delega y revisa después.

Sal del análisis parálisis

¿No sabes si un refactor de verdad simplifica las cosas? ¿Dudas entre dos enfoques de arquitectura? Pídele que implemente los dos. Comparar dos implementaciones concretas es mucho más fácil que discutir dos ideas, y descartar una no le hiere los sentimientos a nadie.

Ejemplo

Dudando entre dos librerías para un editor de texto, un equipo hizo que un agent implementara cada una. Ganó la que dio mejor resultado final. No era la que había sonado mejor en la reunión.

Ten un comando que levante todo

Si cada pull request produce un ambiente donde ver el cambio corriendo, revisar el trabajo de un agent pasa de leer un diff a usar el producto. Para cambios de frontend es la diferencia entre "parece bien" y "está bien". Si no tienes preview deployments, al menos ten un solo comando que levante el proyecto en local, y enséñaselo al agent.

Delegar más

Tareas grandes

Cuando la tarea deja de caber en unos pocos archivos, hacerla de una sola pasada deja de funcionar. Y sin embargo, las tareas medianas y grandes, de una a seis horas de trabajo, son donde un agent rinde más. Dejas de ahorrar minutos y empiezas a recuperar tardes.

Que haga el primer borrador

Para una tarea sustancial, un primer borrador hecho por el agent arranca el trabajo y recorta la mayor parte del esfuerzo. La condición es comunicar el enfoque de entrada. Piénsalo como el arquitecto que dirige a un desarrollador junior: instrucciones claras y detalladas evitan pasar la tarde corrigiendo un malentendido de base.

OficioEl borradorEl refinado
PeriodismoEl reportero junta la información y escribe la primera versión.El editor verifica hechos, corta lo que sobra y decide qué se publica.
CocinaEl ayudante prepara los ingredientes y monta el plato.El chef prueba, ajusta y decide si sale a la mesa.
CódigoEl agent arranca desde el plan y escribe el primer borrador del cambio.Tú revisas el diff, das feedback y haces los retoques antes de mergear.
Ojo

Las tareas grandes no son "manos libres" todavía. Cuenta con dos o tres vueltas de feedback y un retoque final tuyo. Una meta realista es ahorrarte algo así como el ochenta por ciento del trabajo. Tu criterio sigue verificando y firmando.

Planea con él antes de que escriba

Para tareas complejas o mal definidas, armar el plan junto con el agent funciona muy bien. No pasa nada si al principio no conoces todos los requisitos. Empieza con preguntas de descubrimiento: "¿cómo funciona la autenticación aquí?", "¿qué servicios se verían afectados?". Pídele que identifique los archivos concretos que tocaría, para que los confirmes tú antes de que escriba una línea.

Casi todos los agents tienen un modo que solo lee y propone, sin tocar nada; suele llamarse plan mode. Es el sitio correcto para empezar cualquier tarea que no cabe en una frase.

Ponle paradas

Para trabajo en varias partes, sobre todo si cruza varias capas o varios repos, define paradas explícitas:

plan → un pedazo → probar → corregir → tú revisas → el siguiente pedazo

Pide una pausa después de cada fase importante. Usa esa pausa para confirmar que va por donde esperabas, aclarar dudas ("explícame el flujo de auth y confírmame que es seguro") y corregir el rumbo temprano, antes de que un error de base se propague a todo lo demás.

Ejemplo

"Esta feature toca base de datos, backend y dos interfaces. Primero planea el cambio de schema y avísame cuando esté, para aplicar yo la migración." → "Ahora el backend, con tests que cubran X e Y. Avísame cuando termines." → "Ahora las dos interfaces, llamando al endpoint nuevo."

Enséñale a verificar su propio trabajo

Cuando des feedback, no te quedes en "esto no funciona". Explica cómo lo probaste, para que la próxima vez pueda probarlo él. Y si es un procedimiento que vas a repetir, escríbelo donde el agent lo lea siempre (ver Entorno y conocimiento).

Pon tests donde el agent más toca

Hoy un agent no prueba de forma interactiva todos los escenarios. Subir la cobertura justo en las zonas que más modifica te compra confianza barata: con tests sólidos, el código que parece correcto se puede mergear sin ese nudo en el estómago. Los tests felices ya los escribe él; los tuyos son los de error, los vacíos, los negativos.

Ejemplo

Antes de delegarle a un agent traducir una parte crítica de Python a C, un equipo reforzó primero los tests unitarios de esa parte. La traducción después fue aburrida. Aburrida era la meta.

Delegar más

Context y sesiones

La palabra que más explica el comportamiento de un agent es context: lo que puede ver en este momento. Que no es lo mismo que lo que hay en tu repo: es solo lo que de verdad leyó. La distancia entre esas dos cosas explica casi todas las respuestas malas que te va a dar.

Pregúntale qué leyó

Cuando te contesta algo flojo, la reacción natural es pensar que el modelo es tonto. Casi nunca es eso: contestó sin abrir el archivo que de verdad manda. Una línea al final del prompt ayuda mucho aquí: "al terminar, lista los archivos que abriste para responder". Te enseña qué entró al context y, lo más útil, qué se quedó afuera. Cuando empecé, la lista me sorprendía cada vez.

Una sesión es todo lo que lleva acumulado

Cada archivo que leyó, cada cosa que dijiste, cada error que vio. Eso es bueno al principio y malo después: una sesión larga y confundida no se arregla explicándole mejor. Si lo corregiste tres veces y sigue igual, no discutas: sesión nueva, diciéndole exactamente qué leer y cuál es el objetivo. Casi nadie lo hace, y funciona mejor que cualquier otra cosa que conozca.

Ejemplo

"Empecemos de cero. Solo lee estos archivos: [lista]. El objetivo es [una frase]. No toques nada más."

Lo que quieres que sepa siempre, escríbelo

Como cada sesión empieza en cero, todo lo que quieres que sepa siempre tiene que estar en un archivo que lea al arrancar. Casi todos los agents tienen uno: AGENTS.md, CLAUDE.md, un archivo de reglas.2 La dificultad no es escribirlo, es mantenerlo corto: solo lo que no se puede deducir del código, y solo líneas que cambien lo que hace. Si puedes borrar una línea sin que el agent se equivoque, bórrala.

Automatizar

Workflows que corren solos

Un agent reacciona a lo que pasa mucho más rápido que una persona, y está bastante más dispuesto a hacer trabajo aburrido y repetitivo que cualquiera de tus compañeros.

Lo que repites dos veces, déjalo escrito

Todo equipo tiene tareas rutinarias que vuelven cada semana: quitar un feature flag, subir dependencias, agregar tests a los PRs nuevos. Esas son las candidatas. Alguien con experiencia escribe una vez un prompt reutilizable y robusto,3 y de ahí en adelante se corre en vez de reescribirse.

Ejemplo

Hay equipos que disparan automáticamente varios agents dedicados a escribir tests cada vez que se abre un PR con una feature nueva.

Revisión con tus propios errores

Hay herramientas especializadas en revisar PRs rápido. Pero un agent que ya conoce tu repo puede darte algo más útil: revisar contra los errores que tu equipo comete de verdad.

Ejemplo

Mantén en el repo una lista de los errores más comunes del equipo, esos que no se pueden atrapar con un linter. Un agent la lee y revisa cada PR nuevo contra ella.

Reaccionar a alertas e incidentes

Un agent también puede dispararse solo cuando pasa algo: un error nuevo en producción, una alerta, un ticket. Casi todos exponen un CLI o un API para integrarlos a un workflow, y con MCP pueden leer los logs de servicios externos.

Ojo

Para triaje en producción, un agent debuggeando es flojo. En vez de pedirle que arregle bugs de punta a punta según llegan, pídele que marque los errores y cambios más sospechosos. Tú decides.

Automatizar

Entorno y conocimiento

El mismo entorno que el equipo

Nada frena más a un agent que un entorno incompleto o distinto al tuyo. Alinéalo con el del equipo: versiones de lenguaje, dependencias, checks automáticos. Los hooks de pre-commit instalados, los secretos y las variables cargadas solas, el mismo linter que corres tú.

Ejemplo

Un browser con las sesiones ya iniciadas le ahorra al agent, y a ti, cada login manual al probar.

Scripts propios y MCP

MCP es la forma estándar de conectarle herramientas externas: tu base de datos, Jira, Sentry, tu correo.4 Es rápido de probar y hay servidores para casi todo. Pero mucha gente pasa por alto algo más simple: un script de CLI. Un script que baja la info de un ticket dado su ID. Un script que reinicia el entorno local. Herramientas chicas y aburridas para las partes del workflow que se repiten.

Ejemplo

Un equipo escribió un script que muestra solo el primer test que falla, con el detalle completo de ese error. El agent se enfoca en uno a la vez en vez de ahogarse en cien líneas de output, y termina las tareas largas más rápido y con más éxito.

Alimenta su base de conocimiento

Si el agent comete el mismo error dos veces, es momento de escribir el feedback donde lo lea siempre. No le des solo las reglas del framework: cuéntale la arquitectura del proyecto, qué tipo de tests se esperan para cada tipo de tarea, cómo se corren los comandos importantes y qué herramientas prefieres.

Ejemplo

Documentar el procedimiento exacto para agregar una ruta nueva, con cada sitio donde va boilerplate en frontend y backend, convierte esa tarea en algo que se delega sin pensarlo.

En la práctica

Lo que todavía hace mal

Debuggear

Un reporte de bug se ve simple y casi nunca lo es. Muchos bugs necesitan acceso a logs y bases de datos, y un nivel de olfato que la mayoría de los agents no tiene hoy. Si lo usas para debuggear, pídele una lista de causas probables en vez de que arregle todo él. Tú escoges la real; el sistema lo conoces tú. Con la causa en la mano, el arreglo sí vuelve al agent.

Lo visual fino

Los modelos de hoy no tienen el razonamiento visual para cuadrar un diseño con un screenshot o un mockup de Figma al nivel de detalle que hace falta. Les va bien cuando lo visual se puede describir como código: componentes, un sistema de diseño, clases con nombre. Si quieres que respete tu estilo, dale un sistema de diseño del que partir, mejor que una imagen.

Lo que salió después de su entrenamiento

Cuando trabajes con una librería nueva o una versión reciente, pásale el link a la documentación actual. Si no, asume los patrones viejos, porque no sabe que hay una versión nueva. Un buen agent lo supera si le das la doc; ninguno la busca solo.

En la práctica

Perder menos tiempo

No todas las veces que usas un agent salen bien. Hay variación real en los resultados, y parte del trabajo es aprender a usarlo de forma que maximice las veces que sale bien y minimice el tiempo perdido cuando no.

Corta pérdidas temprano

El error más común de quien empieza es empeñarse en que una conversación salga bien cuando el agent ya se desvió. Si te descubres pensando "está ignorando lo que le dije" o "está dando vueltas", esa es la señal. Mandar más mensajes casi nunca lo arregla: lo que dice es que la tarea es más grande que lo que el agent puede hoy. Cierra y toma el control a mano.

Diversifica al principio

Si estás empezando, reparte las apuestas. Prueba tareas y prompts distintos. Descubres rápido en qué es bueno con tu código y en qué no. Dobla la apuesta en lo primero y suelta lo segundo. No le debes a la herramienta que funcione todas las veces.

Empieza de nuevo más de lo que lo harías con una persona

Con un humano, reiniciar la conversación es grosero. Con un agent es la herramienta más efectiva que tienes. Si le diste una tarea y le cuesta corregir el rumbo, una sesión limpia con todas las instrucciones de entrada llega más lejos que una larga llena de correcciones. Un agent arregla un entorno enredado mucho peor de lo que escribe código desde cero.

En la práctica

Seguridad y permisos

Empieza preguntando todo

Cada agent tiene un permission mode: cuánto puede hacer sin consultarte, desde pedir permiso para cada comando hasta no pedir nada. Es más un dial que un interruptor, y dónde lo pones depende de cuánto confías en la tarea, más que en la herramienta. El primer mes, que pregunte todo. Cada permiso que apruebas te enseña qué está a punto de hacer, y saltarse los permisos con una bandera de "no preguntes nada" es la forma más rápida de aprender la lección cara.

Branch antes de tocar

Antes de dejarlo editar en un repo que importa, un branch nuevo. Es la red que convierte "tocó archivos que no esperaba" en un no-evento: descartas y sigues.

Cuentas propias para el agent

Un correo desechable sirve para probar sitios sin riesgo. Si necesita recursos en la nube, dale un rol propio con lo mínimo que necesite. Nunca tus credenciales.

Nada de producción

El agent trabaja donde pruebas tú: local, dev, staging. Idealmente con el mismo setup de pruebas que el resto del equipo. Evita darle acceso a servicios de producción por completo. Con agents remotos, aprovecha que pueden correr un entorno de prueba aislado en su propia máquina.

Keys de solo lectura

Donde se pueda, acceso de solo lectura. Y cualquier script que hable con un servicio de afuera, lo corres tú a mano aunque lo haya escrito él. Una regla aburrida. La vas a agradecer la única vez que importe.

En la práctica

Lo que viene

Los ingenieros no van a ninguna parte. Mientras los agents siguen mejorando, saber de verdad cómo funciona tu sistema vale más, no menos. Ser dueño de tus proyectos y tener criterio sobre ellos es lo que convierte a un agent de un generador de texto en un multiplicador.

Lo que sí cambia es la forma del trabajo. Supervisar varias tareas en paralelo, revisar más de lo que escribes, decidir alcances en vez de teclear implementaciones. En los equipos que van adelante, ese ya es el trabajo. Esta guía es lo que he aprendido preparándome para eso. Ojalá te ahorre algunos golpes.

Notas
  1. Ejemplos de agents autónomos hoy: Claude Code, Codex, Antigravity, Devin, Jules, Cursor en modo agent, opencode. Los locales se pueden correr en varias copias del repo a la vez para lograr el mismo efecto de paralelismo que los remotos.
  2. El nombre cambia por herramienta: AGENTS.md es el más extendido, Claude Code usa CLAUDE.md, Cursor tiene sus rules, Copilot sus instructions. El contenido que va dentro es el mismo.
  3. Cada herramienta le pone su nombre: skills, playbooks, slash commands. Todos son un prompt guardado con un nombre, que se invoca en vez de reescribirse.
  4. MCP, Model Context Protocol, es el estándar abierto para conectar herramientas externas a un agent. Cada servidor conectado le cuesta context al agent en cada sesión, así que conecta los que usas, no los que existen.
